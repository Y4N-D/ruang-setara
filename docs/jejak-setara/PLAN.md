## Keputusan server: paket gratis dulu

Keputusan pemilik proyek, 7 November 2026 (Plan JS-03):

- JS-03 sampai JS-14 memakai paket gratis Cloudflare (Workers Free). Workers Paid diaktifkan sebelum JS-15 atau uji coba kelas pertama, mana yang lebih dulu. Langkah 2 Architecture bagian 18 ditunda sampai saat itu.
- Rancangan menghormati batas paket gratis (Architecture bagian 13.4): CPU 10 ms per permintaan, terutama untuk hash sandi JS-04; 100.000 permintaan Durable Object per hari; dan 100.000 baris tulis per hari, masing-masing untuk SQLite Durable Object dan D1.
- `sim:beban` tidak dijalankan penuh di lingkungan uji sebelum paket berbayar aktif. Uji beban berjalan terhadap Worker lokal.
- Keputusan ini dicatat di PRD bagian 14, 18, dan 21; Architecture JA-03, JA-14, bagian 10.3, 13.2–13.4, 14, 15, dan 18; serta AGENTS bagian 0, 5, 6, dan 7.

## Catatan untuk Plan berikutnya

- Plan JS-03 dan sesudahnya: semua teks yang tampil berasal dari `app/jejak-setara/teks.ts` (Architecture bagian 17). JS-01 membuat berkas itu dengan teks halaman kosong saja, dan JS-02 tidak mengubahnya.
- Semua fitur klien: di repositori ini, tipe `fetch` dan `Response` di kode klien ikut berasal dari `@cloudflare/workers-types` (lewat `tsconfig.json` akar), sehingga hasil `response.json()` bertipe `unknown`. Jawaban server selalu diperiksa dulu, sejalan dengan aturan wajib 3 (`zod`). Ditemukan di percobaan Plan JS-01.
- Plan JS-03: ingatkan langkah 1–6 Architecture bagian 18 (backlog di atas). Putuskan alat uji Worker dan D1 untuk `test:jejak:server` (kemungkinan `@cloudflare/vitest-pool-workers`, perlu izin dependensi; KT-07). **Dijawab di Plan JS-03 (usulan 3):** versi 0.23.0 hanya cocok dengan Vitest 4, sedangkan repositori memakai Vitest 5.
- Plan JS-03: tambahkan lingkungan `uji` dan `produksi` di `server/jejak-setara/wrangler.jsonc`. Karena usulan 1a JS-01 dipakai, lingkungan dipilih saat build lewat `CLOUDFLARE_ENV`, bukan dengan `--env` saat deploy, sehingga langkah Architecture 4.4 berubah menjadi "build dengan `CLOUDFLARE_ENV=uji`, lalu `wrangler deploy`" (dokumentasi Cloudflare, halaman "Cloudflare Environments" plugin Vite).
- Plan JS-03: uji yang memerlukan runtime Workers (`test:jejak:server`) diberi nama atau folder yang tidak cocok dengan pola `test:jejak` (`server/jejak-setara/**/*.test.ts`), atau pola itu disesuaikan, agar `test:jejak` tetap berjalan di Node tanpa runtime Workers.
- Plan JS-03: tanggal kompatibilitas hanya bisa setinggi runtime `workerd` yang terpasang (kini 1.20260515, batas 22 Mei 2026). Fitur Cloudflare yang lebih baru memerlukan kenaikan `wrangler` dan plugin Vite, dengan izin dependensi dan uji ulang versi Vinext yang memakai paket yang sama.
- Plan JS-03: gema WebSocket lewat Worker lokal sudah lulus di Plan JS-01 (kedua cara pengembangan, juga dari halaman di bawah CSP). Durable Object, WebSocket Hibernation, dan D1 lokal belum dicoba.
- Semua fitur, semua sesi: Tailwind galeri membaca seluruh repositori yang tidak diabaikan git, termasuk dokumen, kode, dan skrip Python Jejak Setara (catatan "Semua fitur" di `docs/sehari-setara/PLAN.md`). Diputuskan di Gerbang 1 JS-01 (usulan 13a): setiap ZIP dari sesi mana pun yang menambah atau mengubah berkas teks dicek dengan `build:pages`, dan ke-178 berkas `dist-pages/` harus identik byte dengan build `main`. Bila ada yang berubah, kata pemicunya di berkas baru diganti. Sesi A mengulang pemeriksaan ini di setiap Plan.
- Semua fitur: uji ujung ke ujung Jejak Setara terpisah dari Sehari Setara. Berkas `*.spec.ts` di `e2e/jejak-setara/` ikut terbaca `playwright.config.ts` Sehari Setara, karena folder `e2e/` dibaca beserta subfoldernya (usulan 4).
- Lingkungan agen: `@playwright/test` 1.56.1 mencari Chromium 141, sedangkan yang tersedia Chromium 153 di `/opt/pw-browsers/chromium-1243/`. Satu perintah dibatasi sekitar 300 detik, dan proses latar belakang berhenti di akhir perintah, jadi server uji dinyalakan dan dimatikan di perintah yang sama.
- Lingkungan agen: jangan mematikan proses dengan `pkill -f` atau pencarian pola yang juga tertulis di perintah yang sedang berjalan, karena perintah itu ikut berhenti tanpa keluaran. Server dev dimatikan lewat skrip berkas, dan server uji Playwright lewat `webServer` (laporan JS-01, Temuan 2).

- Hasil percobaan risiko (6 Nov 2026, di luar repositori; Node 22.23.4; `zod` 3.25.76 dan `esbuild` 0.25.0 dipasang di folder percobaan terpisah):
  - **Acak berbenih.** Hash FNV-1a 32 bit atas kode unit string gabungan, lalu pembangkit mulberry32: 97,3 juta angka per detik; uji sebaran chi² 16,5 (df = 15, batas p = 0,05 sekitar 25); 0 tabrakan dari 100.000 benih gabungan `ruang:pemain:kejadian`; benih sama menghasilkan urutan sama dan benih pemain berbeda menghasilkan urutan berbeda; sebaran posisi opsi benar untuk 1.000 pemain adalah 224/250/262/264 dari 250 yang diharapkan.
  - **Gerak dan tabrakan.** Prototipe kotak kaki 10 × 8 px, pemisahan sumbu, dan pemeriksaan kecepatan Architecture 8.2 pada peta sintetis 120 × 80 ubin: 450.000 pesan `gerak` (50 pemain × 10 per detik × 900 detik) selesai dalam 38,2 ms, yaitu **0,08 mikrodetik per pesan**, atau 0,008% dari anggaran 1 ms per pesan (Architecture 13.1). Satu juta pesan tanpa tabrakan memakan 0,04 mikrodetik per pesan. Pada pola gerak realistis, 96% pesan diterima; sisanya ditolak karena menabrak, sesuai harapan.
  - **Skor dan peringkat.** Pengurutan 40 pemain dengan pembanding empat tingkat (Architecture 8.4) memakan 0,0088 ms per hitung (1.000 kali pengulangan).
  - **Protokol dan `zod`.** Prototipe 12 pesan (termasuk `discriminatedUnion` dan `.strict()`): bundel klien 61.102 B sebelum gzip dan **14.647 B gzip**; `safeParse` pesan `gerak` 1,91 mikrodetik; `safeParse` `dunia` berisi 40 pemain 33,85 mikrodetik (pada 10 pesan per detik berarti 0,34 ms per detik). Kunci tambahan ditolak `.strict()`. Ukuran JSON contoh: `gerak` 76 B, `dunia` tiga pemain 98 B, `kunci_1` 57 B, jauh di bawah batas 2 KB.
  - **Bentuk peta.** Grid tabrakan 120 × 80 sebagai larik JSON 19.201 B, sebagai teks RLE 1.526 B pada peta sintetis dengan 2,7% sel padat (anggaran peta gzip 60 KB). RLE dipilih agar `kampung.json` tetap kecil, dengan angka ini sebagai pembanding awal; ukuran sebenarnya diukur di JS-06.
  - **Uji yang ada.** `test:jejak` JS-01 (23 uji) dan `test` Sehari Setara (296 uji) belum dijalankan ulang di Plan; salinan repositori belum memasang dependensi. Pemeriksaan penuh dilakukan di Test JS-02.
- Usulan:
  1. **Batas kerja JS-02.** — (a, saran) JS-02 menulis keenam berkas `inti/` (kecuali `inti/konten/`), menambah skema pesan di `protokol.ts`, dan menulis uji unitnya. (b) JS-02 juga menulis skema konten dan pembaca peta lengkap: lebih cepat untuk Sesi B, tetapi menyerobot berkas yang menjadi tanggung jawab sesi lain dan memperbesar risiko tabrakan kerja paralel. (c) Peta ditunda seluruhnya ke JS-06: JS-02 hanya menulis gerak, tetapi tabrakan tidak bisa diuji tanpa grid, sehingga JS-02 akan menunggu Sesi C.
  2. **Bentuk `kampung.json` dan pembaca `inti/peta.ts`.** — (a, saran) satu JSON berversi: `versi`, `lebar`, `tinggi`, `ukuranUbin`, `ubin` dan `tabrakan` sebagai string RLE (`"0x12;1x5;…"`), daftar `objek`, batas `zona` (z1–z8), `titikKejadian` per zona (dengan id), `kotak`, `halte`, `gerbangLobi`, dan `titikMuncul`. `bacaPeta` memeriksa isi dengan `zod` dan menolak berkas yang tidak cocok; `ubin` disimpan untuk JS-07, `tabrakan` dipakai `gerak.ts`. Architecture 11.1 diberi bentuk ini agar Sesi C membangun ke bentuk yang sama. (b) Larik angka untuk setiap lapisan: mudah dibaca manusia, tetapi 19 KB per lapisan dan mendekati anggaran peta. (c) Bitmask base64: paling kecil, tetapi sulit ditinjau dalam *diff* dan sulit dibuat `build_peta.py`.
  3. **Tabrakan.** — (a, saran) kotak kaki 10 × 8 px logis di posisi pemain (titik kaki), diperiksa per ubin 16 px, dengan pemisahan sumbu (gerak X lalu Y) agar avatar meluncur di dinding dan tidak tersangkut di sudut. Batas peta padat. Pemain saling tembus (PRD 8.2). (b) Tabrakan titik: paling sederhana, tetapi avatar setengah masuk dinding dan terasa kasar. (c) Lingkaran radius 5 px: sudut lebih halus, tetapi perhitungan lebih mahal dan kotak kaki lebih sesuai gaya piksel.
  4. **Pemeriksaan gerak di server.** — (a, saran) fungsi murni `periksaGerak` yang menerima posisi terakhir yang sah, laporan baru, selang waktu, kecepatan saat itu (72 px/detik atau 115,2 saat Lari cepat), dan grid tabrakan; tolak bila jarak melebihi kecepatan × selang × 1,25 + 4 px, atau posisi menabrak, atau status bukan `main`, atau dialog terbuka. Diagonal dinormalisasi. `seq` yang lebih kecil dari yang terakhir diabaikan. Hasilnya `{ diterima, posisi }` untuk dikirim sebagai `koreksi`. (b) Tanpa toleransi 1,25 + 4 px: lebih ketat, tetapi klien di jaringan lambat akan sering dikoreksi dan terasa tersentak. (c) Pemeriksaan di klien saja: tidak memenuhi aturan wajib 2.
  5. **Acak berbenih.** — (a, saran) `benih(...bagian)` = FNV-1a 32 bit atas string bagian yang disambung dengan `;`, lalu `acakBerbenih(benih)` = mulberry32; disediakan `kocok`, `pilih`, dan `bulat` yang semuanya memakai pembangkit itu. Benih ruang, id pemain, dan id kejadian disusun dengan urutan tetap; tidak ada `Math.random` di `inti/`. Angka percobaan di atas menunjukkan sebaran baik dan hasil sama di mesin mana pun. (b) `xorshift128+`: periode lebih panjang, tetapi lebih banyak kode dan keadaan yang harus disimpan bila urutan perlu dilanjutkan. (c) `crypto.getRandomValues`: tidak bisa diulang, sehingga penempatan tidak sama antarpemain dan tidak bisa diuji.
  6. **Skor dan peringkat.** — (a, saran) `hitungPoin(langkah1Benar, tingkat)` memakai konstanta `POIN` (40/60/25/0); `bandingkanPeringkat` mengikuti empat tingkat Architecture 8.4; `hitungPeringkat` mengembalikan larik berurut dan nomor peringkat 1..n. Karena tingkat keempat (urutan bergabung) selalu berbeda, tidak ada peringkat kembar. (b) Peringkat kembar untuk skor sama: lebih mudah dibaca, tetapi bertentangan dengan aturan "lebih dulu mencapai skor itu". (c) Hitung peringkat di klien: bertentangan dengan server berwenang.
  7. **Skill dan kotak.** — (a, saran) tabel `SKILL` di `aturan.ts` (muatan maks 2, kecuali Teropong dan Angkot 1; lama Lari cepat 6 detik, Kompas 20 detik; jeda pemakaian skill yang sama 2 detik; Petunjuk hanya di Langkah 1) dan fungsi murni `bolehPakaiSkill`, `pakaiSkill`, `tambahMuatanKompas` (batas 2, dipanggil pada jawaban "tepat"), `kotakSiap` (muncul lagi 90 detik per pemain, jangkauan ambil 12 px). Skill yang dimatikan guru datang dari `PengaturanRuang.skillAktif`. (b) Tabel di D1/pengaturan: bisa diubah tanpa deploy, tetapi menambah kueri dan versi; nilai PRD 8.5 masih akan ditimbang ulang sesudah uji coba kelas. (c) Angka tersebar di kode: sulit diuji dan diubah.
  8. **Masa dan jam cerita.** — (a, saran) pemetaan lurus: menit cerita = 360 + 720 × kemajuan (0 → 06.00, 1 → 18.00), dibulatkan ke bawah; masa ditentukan dari ambang 30% dan 65%, dengan batas bawah inklusif dan batas atas eksklusif (0 ≤ p < 0,3 pagi; 0,3 ≤ p < 0,65 siang; 0,65 ≤ p ≤ 1 sore). Kemajuan dihitung dari waktu ronde tanpa lama jeda. "Dua menit terakhir" bila sisa ≤ 120 detik. Malam bukan hasil pemetaan; itu status layar akhir. Rumus lurus menghasilkan 09.36 dan 13.48 persis seperti tabel PRD 8.1. (b) Tabel potongan tiga baris: sama hasilnya di dalam potongan, tetapi jam di dalam potongan tidak bergerak mulus. (c) Jam dinding sungguhan: tidak sesuai "langit sehari".
  9. **Skema protokol dan `zod`.** — (a, saran) semua pesan v1 memakai amplop `{ v: 1, t: "…" }` dengan `discriminatedUnion` pada `t`, `.strict()` agar kunci tambahan ditolak, dan batas angka/teks yang sama dengan Architecture 6.6 (misalnya `nomorAbsen` 1–50, `seq` bilangan bulat, token 43 karakter base64url). Server memakai skema yang sama di JS-03; klien memakai `safeParse` untuk pesan yang diterimanya. Biaya terukur 14,6 KB gzip dan 1,9–33,9 mikrodetik per pesan, sehingga layar pemain menjadi sekitar 76 KB dari anggaran 200 KB. (b) Klien hanya memakai tipe tanpa `zod`: hemat 14,6 KB, tetapi pesan server yang cacat bisa merusak tampilan tanpa pesan galat yang jelas. (c) Skema ditulis di server saja: klien dan server bisa berbeda paham, bertentangan dengan JA-07.
  10. **Uji kemurnian `inti/`.** — (a, saran) satu uji Vitest yang membaca semua berkas `inti/**/*.ts` dan gagal bila menemukan impor `react`, `next`, `node:*`, `@cloudflare/*`, atau `server/`; atau panggilan `Date.now`, `Math.random`, `performance.now`, `crypto`, `fetch`, dan `localStorage`.   11. **Teks yang tampil.** — (a, saran) JS-02 tidak mengubah `app/jejak-setara/teks.ts`, karena inti tidak menampilkan teks; kode galat protokol (Architecture 6.7) adalah konstanta, dan kalimatnya dipakai JS-03. ### Rincian C-8 (kapasitas 100 pemain per ruang)

Angka dari percobaan Plan JS-03 di atas. Lalu lintas dan kuota memakai batas 24 pemain terdekat di `dunia`.

| Ukuran | 40 pemain | 100 pemain | Batas atau anggaran |
|---|---|---|---|
| Pesan masuk ke ruang | sekitar 300 per detik | sekitar 740 per detik, sampai sekitar 1.000 bila semua bergerak | Batas lunak sekitar 1.000 per detik per Durable Object |
| Lalu lintas turun per pemain dalam 15 menit | sekitar 1,5 MB | sekitar 2,5 MB | 3 MB (PRD 12) |
| CPU satu putaran 100 ms (Node) | 0,03 ms | 0,16 ms | 10 ms per peristiwa (paket gratis) |
| Permintaan Durable Object per sesi | sekitar 13.600 | sekitar 33.500 | Gratis 100.000 per hari; berbayar 1 juta per bulan termasuk |
| Sesi per hari di paket gratis | sekitar 7 | sekitar 3, tepat di batas | — |
| Tagihan di paket berbayar | Tetap US$5 sampai sekitar 70 sesi per bulan | Tetap US$5 sampai sekitar 30 sesi per bulan, lalu sekitar US$0,005 per sesi | Anggaran Rp 500.000 per bulan |

- Secara teknis satu ruang muat untuk 100 pemain, asalkan syarat usulan 11a dipenuhi: batas 24 pemain terdekat di `dunia`, `gerak` paling banyak 6 kali per detik di ruang besar, dan batas protokol 100.
- Peta 160 × 100 menyediakan 96 titik kejadian (12 per zona). Dengan dua titik aktif per kejadian, satu paket bisa memuat sampai 48 kejadian (6 per zona). Dua titik aktif mengurangi kerumunan dan memperpendek jalan, tetapi peta terasa lebih mudah dijelajahi; karena itu hanya untuk ruang lebih dari 50 pemain.
- Kejadian lebih banyak per ronde berarti naskah dan rujukan baru (Sesi B) yang juga harus diverifikasi. Disarankan diputuskan sesudah uji coba kelas, dengan Paket inti 16 tetap untuk rilis 1.0. Guru juga bisa menambah kejadian lewat konsol (JS-12).
- Ruang 100 pemain biasanya gabungan beberapa kelas, sehingga nomor absen bisa kembar. Karena itu mode nomor absen hanya untuk ruang sampai 50 pemain.
- Di paket gratis, satu percobaan 100 pemain di lingkungan uji memakai sekitar sepertiga kuota harian, jadi percobaan seperti itu menunggu paket berbayar.

### Yang perlu disiapkan pemilik proyek sebelum Build JS-03

Langkah lengkapnya di Architecture bagian 18. Semua dengan paket gratis.

1. Buat akun Cloudflare di cloudflare.com (langkah 1). Tidak perlu kartu.
2. Buat basis data D1 bernama `jejak-setara-uji` di menu Storage & Databases → D1, lalu kirim **Database ID**-nya kepada Sesi A (langkah 3). ID ini bukan rahasia.
3. Buat token API di My Profile → API Tokens → Create Token, dengan templat "Edit Cloudflare Workers" ditambah izin D1 Edit (langkah 4). Jangan kirim token ke chat.
4. Catat Account ID di halaman Workers & Pages (langkah 5).
5. Simpan `CLOUDFLARE_API_TOKEN` dan `CLOUDFLARE_ACCOUNT_ID` di GitHub → Settings → Secrets and variables → Actions → New repository secret (langkah 6).
6. Lewati langkah 2 (Workers Paid) sampai sebelum JS-15 atau uji coba kelas pertama.

Bila nomor 2 sampai 5 belum selesai saat Build dimulai, Build dan uji lokal tetap berjalan, dan deploy ke lingkungan uji menyusul begitu ID dan rahasia tersedia (usulan 5a).
